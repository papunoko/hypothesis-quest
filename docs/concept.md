# 仮説クエスト — 企画詳細

最終更新: 2026-09-20
原典: [research/chatgpt-rally.txt](research/chatgpt-rally.txt) / 絞り込みの経緯: [decisions.md](decisions.md)

## 1. 前提となる問題

AIは大量に成果物を作れるが、**人間の理解が追いつかない**。
そして「わかりやすい解説」を足しても、**わかった気**にしかならない。

解説を読む体験には、次の欠陥がある。

- 説明する側が順番と着地点を決めている（読み手に疑問が生まれない）
- 読んだかどうかしか観測できない（理解したかは誰も知らない）
- 「そもそもこの仕様がおかしい」という発見が成功に数えられない

## 2. 解き方

**説明を聞く人ではなく、説明を作る人にする。**

プレイヤーは、AIが書いた機能について「この仕組みが守ろうとしているルール」を自分の言葉で書く。
システムは正誤を採点しない。代わりに、**その説明では扱えない事例**を見つけて差し出す。

目指す状態は「説明を聞いてわかった気がする」ではなく、
**「この成果物で、自分なりに遊べるくらいわかった」**。

### 主役にする気持ちよさ（3つだけ）

1. **つながった** — 別々に見えた事例が、一つの見方で説明できる
2. **自分の考えが効いた** — 自分が書いた仮説によって、次に出る事例が変わる
3. **一緒に考えると面白い** — 相棒が考えを受け止め、次の一手を示す

明確に避けるもの: 読了バッジ、連続ログイン、減点、理解度スコア、AIによる「素晴らしい発見です！」の連発。

## 3. 一巡のループ

```
 ┌──────────────────────────────────────────────┐
 │ ① あなたが一文の仮説を書く（自由文）        │
 └───────────────┬──────────────────────────────┘
                 ▼
 ┌──────────────────────────────────────────────┐
 │ ② Jev: この仮説に従うと、各事例の結果は？    │
 │    「増える / 増えない / 仮説では決まらない」 │
 │    ※ 実際の結果は Jev に渡さない             │
 └───────────────┬──────────────────────────────┘
                 ▼
 ┌──────────────────────────────────────────────┐
 │ ③ コード: 予想 vs 事前検証済みの実際の結果    │
 └───────────────┬──────────────────────────────┘
                 ▼
 ┌──────────────────────────────────────────────┐
 │ ④ 食い違う未提示の事例を1枚選んで出す         │
 │    （なければ「決まらない」事例を出す）       │
 └───────────────┬──────────────────────────────┘
                 ▼
 ┌──────────────────────────────────────────────┐
 │ ⑤ 相棒「この違いは、今の説明に入ってる？」    │
 │    → 仮説を書き直す（①へ戻る）              │
 └──────────────────────────────────────────────┘
```

仮説の履歴は画面に残す。**自分の考えがどう変わったかが見えること自体を報酬にする。**

```
最初：同じ商品は登録しない
  ↓
いま：同じ依頼の再送では、新しい登録を増やさない
```

## 4. 題材

> **位置づけ（2026-09-20 決定）**: この節の注文登録API（題材1）は **開発用ダミー**。骨格・Jev 呼び出し・事例選択を作るための架空の題材で、デモには使わない。
> **本番題材は [subjects/lru-cache.md](subjects/lru-cache.md)（`functools.lru_cache`）。** 実イシュー由来の事例8枚と、30行の戻り先を持つ。

AIが書いた架空の **注文登録API**。

```
POST /orders
Idempotency-Key: <依頼ID>     ← 再送を識別するための鍵
{ "productId": "A", "qty": 1 }
```

守りたいこと: **通信の再送で勝手に2件登録されるのは困る。でも、意図して2件注文するのは許したい。**

### 事例カード（6枚・すべて事前に動作検証してJSONに固定）

| ID | 状況 | 依頼ID | 商品 | 実際の結果 |
| --- | --- | --- | --- | --- |
| **C1** | 初回の登録 | K1 | A | 1件（201） |
| **C2** | 同じ依頼の再送 | K1 | A | 1件のまま（200・最初の結果を返す） |
| **C3** | 意図して2件目を注文 | K2 | A | 2件（201） |
| **C4** | 同じ依頼IDで中身が違う | K1 | **B** | 登録されない（409 競合） |
| **C5** | 再送のたびに依頼IDを作り直す | K3→K4 | A | **2件**（重複を防げない） |
| **C6** | 依頼IDを付けずに再送 | なし | A | 2件 |

### 仮説がどう壊れていくか（＝ゲームの深さ）

仮説は「どう判定するか」ではなく **「この仕組みは何を守っているか」** を書かせる（入力欄の問いもそう書く）。
結果の軸は件数だけでは足りない（下の注）。**4択**にする。

| プレイヤーが書きがちな仮説 | 破る事例 | 予想 → 実際 | そこで見えるもの |
| --- | --- | --- | --- |
| 「同じ商品は重複して登録しない」 | **C3** | 増えない → 登録される | 商品の同一性では、意図的な2件目まで止めてしまう |
| 「同じ依頼IDなら1件のまま」 | **C4** | 同じ結果 → **拒否** | 同じ鍵で中身が違うときにどうするかを、まだ決めていない |
| 「再送では登録を増やさない」 | **C5** | 増えない → 登録される | **誰がいつ依頼IDを発行するか**が仕様の一部だった |

C5は特に重要。「ならIDを毎回作り直したら？」という**プレイヤー自身から出る疑問**が、そのまま次の事例になる。

> **注（当日の grill で判明）**: 結果軸が「増える／増えない」だけだと、C4 は「増えない＝一致」、C5 は「IDが違うので増える＝一致」となり反証にならない。
> C4 は「増えないが拒否される」、C5 は「予想通り増えるが、守りたいことが守れていない」事例なので、
> 応答の種別を軸に入れ、仮説を「守りたいこと」の向きで書かせることで初めて両方が反証として働く。

### 本番の題材

- **題材2: functools.lru_cache** → [subjects/lru-cache.md](subjects/lru-cache.md)（事例8枚・2011〜2021年の実イシューに対応・戻り先は純Python 30行の `_make_key`）。注文APIと同じ「同じなら二度やらない」構造なので、題材1で作った骨格・事例選択ロジックをそのまま流用する
- 載せ替え時に決めること: 設計B の軸（値／書き方／順番／型／引数1個の特例）、L8（unhashable）の扱い、検証スクリプトの置き場所。→ [backlog.md](backlog.md) T-60〜

## 5. Jev 呼び出し設計

> **現状のコードはこの節と違う（2026-09-20 中断時点）。** 下の「事例ごとに Choice」は設計A。Jev が状況文に引っ張られて仮説を適用できなかったため、
> `src/lib/jev.ts` は **設計B: 仮説文だけを Noul 4軸で読み、当てはめはコード** に切り替えてある。どちらもまだ安定していない。実測と次の手は [HANDOFF.md](HANDOFF.md)。

### リクエスト（設計A: 事例ごとに Choice）

state は事例ごとに違うので **1事例＝1リクエスト**。未提示の事例ぶんを並列で投げる。

```
state:
  世界の説明（注文を送ると登録される。商品・数量・任意の依頼ID）
  「プレイヤーの仮説が、このAPIの唯一のルールだとしたら」という枠組み
  プレイヤーの仮説（一文）
  状況 ＋ 操作列（結果は含めない）

question (Choice): 仮説を唯一のルールとして適用したとき、最後の操作の結果は？
  criteria:
    created      — 新しい注文として登録される（件数+1）
    same         — 登録は増えず、以前と同じ結果が成功として返る
    rejected     — 登録は増えず、エラーとして拒否される
    undetermined — 仮説はこの状況に触れているが、一通りに読めない
```

- **実際の結果は Jev に渡さない。** 照合は後段のコードが行う
- 1事例＝1問。複合条件を1問に詰めない
- 「この仮説だけでは決まらない」を必ず選択肢に入れる ←（仮説の**穴**を検出する経路）

**当日のチューニングで学んだこと**

1. 「補って推測するな」と書くと Jev は全事例 undetermined に逃げる。「仮説を唯一のルールとして機械的に適用する」「仮説の条件に当てはまらなければ通常どおり登録される」と**デフォルトを与える**必要がある
2. state に `Idempotency-Key` という語があると、Jev は仮説より冪等キーの一般知識で判断する（「同じ商品は重複しない」で C3 を「登録される」と読む）。**実装の手がかりになる語を Jev に見せない。** 依頼ID・商品・数量と日本語で書き、「仮説に出てこない要素は結果に影響しない」と明示する

### 事例の選び方（コード側）

```
1. 予想 ≠ 実際 の未提示事例があれば、それを出す         （反証）
2. なければ「仮説だけでは決まらない」の事例を出す        （適用範囲の穴）
3. どちらもなければ、未提示の事例を出す
4. 全事例が一致して尽きたら —— 「正しい」とは言わない：
   「用意した6事例では、この説明で説明できました。
     ただし確認したのはこの6つだけです。」＋ 未確認の論点を出す
```

### confidence の扱い

低confidence ＝ 理解不足ではない。**解釈の確認に回す。**

> 「あなたの仮説だと、この場合も登録は増えない、という読み方で合ってる？」 [はい / いや、違う]

**Jevの読み間違いを、プレイヤーの間違いにしない。** confidence は選択肢の確率分布から出る指標であって、プレイヤーの理解率ではない。

閾値は **0.55**（D-01、`page.tsx` の `CONFIDENCE_THRESHOLD`）。画面では「確信度」と表示し、「理解度」とは書かない。

## 6. 不可侵のルール（vibe と正確性の境界）

自由にしてよいもの / 絶対に動かしてはいけないもの を分ける。

| 自由にしてよい | 動かしてはいけない |
| --- | --- |
| 問い・状況設定・語り口・探索の順番 | **確認済みの事実と実行結果** |
| 「この制約を外したら？」という仮想条件 | 事例カードの結果（事前検証済み・固定） |
| プレイヤーが持ち込んだ別の整理 | 記録されていない設計意図 |

- **AIにその場で反例を創作させない。** 事例は6枚の固定データ
- 設計意図が記録されていないなら、**「理由未記録」という事実そのもの**を探索対象にする。もっともらしい理由を捏造して「本当の制作意図」にしない
- 見た目を気持ちよくするために、未確認の仮説を「証明完了」のように演出しない

## 7.「省略しない」をどう担保するか

原文リンクを置くだけでは足りない。**気づかないまま終わるなら、体験としては省略されている。**

1. **対象範囲を明示する** — 「この機能の、この論点」と最初に言う。「成果物全体を理解した」とは絶対に表示しない
2. **未探索を見せる** — 未確認の論点の**存在**は最初から見える。中身を開いていなくても「通信失敗についてまだ調べていない領域がある」とわかる
3. **複数の入口を用意する**（Three Clue Rule）— 同じ論点に、画面操作からも、事例比較からも、業務上の理由からも辿り着ける。証拠の水増しではなく、**気づく経路を複数作る**
4. **「見せた」と「理解できた」を分ける** — 表示しただけで理解済みにしない。かといって採点もしない。残すのは観察できた行動:
   ```
   ✓ 通常の登録は試した
   ✓ 再送との違いは説明できた
   ─ 複数端末の場合は未確認
   ```
5. **終了時に未探索を消さない** — 「クリア！」で終わらせず、わかったこと / 残っている論点 / 成果物側の不明点を残す。仕様と実装が食い違っていたら、それは**プレイヤーの理解不足ではなく、世界の側がまだ整っていないという発見**として扱う

## 8. 画面構成（1枚）

```
┌─────────────────────────────────────────────────────┐
│ 対象: 注文登録API / 論点: 再送と重複        [地図▾]│
├──────────────────────────┬──────────────────────────┤
│                          │  いまの仮説              │
│   比較する事例           │  ┌────────────────────┐  │
│  ┌────────────────────┐  │  │ 同じ依頼の再送では │  │
│  │ C2 同じ依頼の再送  │  │  │ 登録を増やさない   │  │
│  │   予想 1件/実際 1件│  │  └────────────────────┘  │
│  │ C3 意図的な2件目   │  │       [書き直す]         │
│  │   予想 1件/実際 2件│  │                          │
│  │        ↑ 食い違い  │  │  履歴                    │
│  └────────────────────┘  │   1. 同じ商品は…        │
│                          │   2. 同じ依頼は…  ←いま │
│  相棒                    │                          │
│  「この違いは、今の説明  │  調べたこと              │
│    に入ってるかな？」    │   ✓ 通常の登録           │
│                          │   ✓ 再送との違い         │
│                          │   ─ 複数端末（未確認）   │
├──────────────────────────┴──────────────────────────┤
│ ▸ 根拠を見る（設計メモ / コード / テスト）          │
└─────────────────────────────────────────────────────┘
```

### 操作は3つだけ

| 操作 | できること |
| --- | --- |
| **こういうこと？** | 仮説を自由文で書く・書き直す |
| **この例で試す** | 提案された事例を開き、予想と実際を比べる |
| **助けて / 根拠を見る** | ヒント、説明、元の設計メモ・コードを開く |

ヒントは段階を付ける（正解を出さない）:
「2つの事例を並べてみますか？」→「商品コード以外で違う値を探してみて」→「ここでは依頼IDが違います」

毎回なにか答えないと進めない設計にはしない。疲れているときに試験を受けさせない。

## 9. 唯一残す"欲" — コードへ戻る導線

各事例から、**元の設計メモ・コード・テストへ戻れること**は切らない。
最後に「いま発見した区別が、このコードのどこに表れているか」を見せる。

**これがないと、Jevを使っただけの普通のプログラミング学習ゲームになる。**

## 10. 初版でやらないこと

- 生成LLM（相棒の台詞は事例ごとの定型文で足りる）
- キャラクター設定・長期記憶・マルチエージェント会話
- リポジトリの自動読み取り・RAG・任意の成果物の取り込み
- 題材の自動生成
- React Flow による探索地図（テキストの一覧で足りる）
- 経験値・レベル・バッジ

理由: **この一巡が面白いかどうかを先に確かめるため。**

## 11. 試遊で観察すること

感想の「楽しかった」は指標にしない。見るのは次の区別。

| 観察されたこと | 何の問題か |
| --- | --- |
| やりたいことはあるが、操作方法がわからない | インターフェース |
| 操作できるのはわかるが、何をしたいとも思わない | 状況・目的・好奇心の設計 |
| 操作しても、自分の意図が結果に届いた感じがしない | フィードバック |
| 楽しく進んだが、別の例では考え方を使えない | 理解・転用の設計 |

最重要: **プレイヤーが自発的にやりたくなったが、用意していなかった行動。**
出たら何でも足すのではなく、3つの操作で受け止められるかをまず考える。

## 12. 公開構成

ハッカソンでの共有は、ローカルの Next.js 本番サーバーを Cloudflare Tunnel で
公開する。`/api/predict` は Next.js の Node.js ランタイムで動かし、`JEV_API_KEY` は
公開元の `.env.local` にだけ置く。

この構成では `cloudflared` を使い、Wrangler は使わない。公開元のPC、`npm start`、
`cloudflared` のいずれかが停止すると公開も終了する。手順は [deployment.md](deployment.md)。
