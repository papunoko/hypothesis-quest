# 意思決定の記録 — なぜ「仮説クエスト」1本に絞ったか

最終更新: 2026-09-20
決定: **[仮説クエスト](concept.md)** を唯一の実装対象とする

---

## 1. 決定に使った2つの問い

8案を並べても決まらなかったので、アイデアの中身ではなく**制約と好み**を先に固定した。

| 問い | 答え |
| --- | --- |
| 終了直後、何と言わせたら勝ちか | **「これ自分で触ってみたい」**（体験で殴る。実用性でも技術的必然性でもない） |
| いちばん避けたい事故は | **動いたけど「で？」と言われる**（誰の何がうれしいか伝わらない） |
| 「で？」を回避する物語をどこから持ってくるか | **自分が実際に困っていること**（AI成果物の理解がしんどい） |

この3つで、8案のうち7案が落ちた。

## 2. 落ちた案と、その理由

| 案 | 内容 | 落ちた理由 |
| --- | --- | --- |
| **A** Three Clueリンター | 「省略しない」を意味的静的解析にする | 「便利」側で、**触りたさ**がない。CIで裏に回る |
| **B** 解釈が見える入力欄 | confidenceをUXに出す | 単体ではUI部品で、**物語がない**（→ ただし吸収。§3） |
| **C** 語りの検問所 | 発話に出所ラベルを付ける | 物語がTRPG卓の文脈になり、**自分の困りごと**から離れる |
| **D** ドキュメント整合linter | 文書群の意味的ドリフト検知 | 「便利」側。触りたさがない |
| **E** 会議サポート（発話タイミング） | 「いま喋るべきか」を判定 | 着眼は最強だが物語が営業・商談に寄る。**音声前段が必須**で実装も重い |
| **F** 迷い検知ガイド | 詰まっている瞬間を捕まえる | 一般論になり「で？」を食らいやすい |
| **G** YouTube区間抽出 | 字幕からイベント区間を取る | 既存OSSが厚い（sponsor-detection / jevmeter）。誰の痛みか弱い |

## 3. 落ちていない案 — B は吸収される

**B（解釈が見える入力欄）は2個目のアイデアではなく、仮説クエストの中核UIである。**

仮説クエストには「Jevがあなたの仮説をこう読み取りました、合ってますか？」という訂正画面が必ず要る。それがBそのもの。

- Jevの読み間違いを、プレイヤーの間違いにしないために必要
- 低confidenceを「理解不足」ではなく**解釈の確認**に変換する装置
- → [roadmap.md](roadmap.md) の **P3**

他の案も、この骨格の上には乗る（→ roadmap.md「将来」）。**逆は成立しない** —— A〜Gのどれかを先に作っても、仮説クエストはそこから生えてこない。

## 4. 採用理由

| 勝ち条件 | 仮説クエストがどう満たすか |
| --- | --- |
| 触ってみたい | 審査員に入力欄を渡せる。**何を書いてもいい**（用語不要・外してもいい）。書いた内容で次の事例が変わる |
| 「で？」を食わない | 「AIの成果物が理解できない」は会場の全員が今日抱えている痛み |
| 物語が自分のもの | 「読むのをやめて、自分の説明を書く」という反転が30秒で語れる |
| LLMでよくね、への反論 | **Jevに正解を判定させない**構造（下記） |

### 「LLMでよくね？」への構造的な回答

```
ユーザーが自然文で仮説を書く
  ↓ Jev  : この仮説に従うと結果はどうなる？（Choice）※実結果は渡さない
  ↓ コード: 予想 vs 事前検証済みの実結果 を照合
  ↓ 食い違う未提示の事例を出す
```

Jevは**正解を判定していない。仮説を読み取っているだけ。** その結果:

- AIが反例を捏造できない（事例は事前検証済みの固定データ）
- 「AIに理解度を採点される」不快感が構造的に発生しない
- confidence は理解率ではなく、**解釈の確信度**として正しく使われる

役割分担がきれいに割れていることが、そのまま企画の説得力になっている。

## 付録A — 判断軸（他の案を評価するときも使う）

「それLLMでよくね？」への一般解。**次の4軸のどれかに当たるならJev。どれにも当たらないならLLMで良い。**

| 軸 | 条件 | Jevが勝つ理由 |
| --- | --- | --- |
| **R** 回数 | 判定が N×M / 毎行 / 毎フレームに増殖する | 組合せ爆発を単価で殴れる |
| **L** 遅延 | 間に合わない判定は価値ゼロ | 70–500ms帯 |
| **P** 確率 | 確率・信頼度**そのもの**が成果物 | 校正された確率が返る。LLMの自己申告スコアは校正されていない |
| **T** 型 | 出力が文章でなく `if` で良い | パースもリトライも要らない |

仮説クエストは **T**（Choiceがそのまま照合ロジックに入る）と **P**（confidenceを解釈確認に使う）で立っている。
※ ハッカソンの勝ち条件が「体験」だったため、**この軸は決定打にはならなかった**。軸で選ぶならAかEだった。

## 付録B — 各案のJev設計（将来の参照用）

落とした案も、設計まで落としたものは残しておく。

- **A** 「この手がかりは結論Xを指すか」Noul を 手がかり×結論の全ペアに → `count(p>=thr) < 3` で警告。数え上げはコード
- **C** 「この発話は資料に根拠があるか」Noul ＋ 出所種別（資料/過去ログ/アドリブ/矛盾）Choice
- **D** 「この差分は当該文書と矛盾するか」Noul、ドリフト度Score。観点は別々のNoulに割る
- **E** 「いま割り込むべきか」Noul ＋ 種別Choice。低confidence＝黙る
- **F** 「迷っているか」Noul ＋ 詰まり箇所Choice。案内文の生成だけLLM
- **G** 字幕行ごとに「この行はイベントXの開始か」Noul → 連続区間に畳む

公開事例の調査: [research/jev-use-cases.md](research/jev-use-cases.md)
