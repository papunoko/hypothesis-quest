# 注文APIの動作確認デモ（約2分）

注文APIは開発用題材。本番のlru_cache向け台本は別途T-54'で作成する。

## 事前確認

`npm run dev`で起動し、ブラウザで開く。`.env.local`にJEV_API_KEYが必要。
`npm run eval:jev` または `npm run test:e2e:live` で実Jevの分岐を確認する。
モデルの読みが変わる可能性があるので、低い判定強度は「解釈の確認」として紹介する。

## 冒頭30秒

「AIが書いたコードを、説明を読んでわかったつもりになってしまう。そこで自分の言葉で、何を守っている仕組みなのかを書いてみます。すると、その説明と食い違う具体例が出てきます。Jevは理解度を採点せず、私の仮説を読み取ります。実際の結果は、コードを実行して確かめた固定の事例です。」

## 30〜65秒: 商品を基準にする

入力: `同じ商品は重複して登録しない`

期待: C3「意図して2件目を注文」。予想は「前と同じ結果」、実際は新規登録。
「商品は同じでも、依頼IDを変えると2件になる。商品が同じかどうか、だけでは説明できません。」

## 65〜100秒: IDを基準に書き直す

入力: `同じ依頼IDなら、登録は1件のまま`

期待: C4「同じ依頼IDで中身が違う」。予想は「前と同じ結果」、実際は拒否。
「登録が増えないという点は合っていても、成功と拒否は違います。説明に中身の一致が抜けていました。」

## 100〜120秒: 次の仮説と未確認事項

入力例: `同じ依頼IDで同じ中身なら前の結果を返す。同じ依頼IDで中身が違えば拒否する`

「この説明なら用意した事例を説明できそうです。でも、再起動や別の顧客のID衝突までは確かめていません。理解したつもりの範囲と、まだ確かめていない範囲が残ります。」

全6事例を表示して終了しても、画面は正解認定をしない。
接続に失敗した場合は「予想なしで次の事例を開く」で実結果を確認する。

## 実装メモ

[TypeSafeのNoul仕様](https://docs.typesafe.ai/primitives/noul)に従い、独立した4問を1リクエストで評価する。
返る値はyes確率。画面の判定強度はその確率から計算したアプリ独自の指標で、正答確率ではない。
