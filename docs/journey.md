## 0. 導入 — あなたはメンテナで、PR をレビューする

プレイヤーに「仮説を書け」と言っても、どの向きで書けばいいか分からない。**レビュワーの気持ち**に立たせると向きが決まる（2026-09-20 の着想）。

冒頭の語り（30秒・T-55）:

> あなたは CPython の `functools` のメンテナです。
> 今日、こんな PR が届きました。
>
> **PR #: 「lru_cache: typed=False のとき f(1) と f(1.0) を同じ呼び出しとして扱う」**
> 作者いわく「1 == 1.0 なのにキャッシュが外れるのはバグ。`_make_key` の近道を外せば直る。テストも足した」
>
> マージしていいか判断するには、**いまの実装が何を「同じ呼び出し」とみなしているか**を、あなた自身の言葉で言えなければならない。
> 一文で書いてください。書いたら、テストスイートがあなたの説明を試します。

この PR は架空だが、中身は **bpo-39554（2020年）の報告者の期待そのもの**。つまりプレイヤーは、作者本人（Raymond Hettinger）が実際にした判断を追体験する。

### 枠組みが変えること

| 要素 | 枠組み前 | 枠組み後 |
| --- | --- | --- |
| 仮説の向き | 「この仕組みは何を守っている？」（抽象） | 「マージ判断のために、現状の振る舞いを一文で言う」（具体・当事者） |
| 事例カード | 出題 | **テストスイートと、過去に届いたバグ報告**。「このテスト、あなたの説明だと通る？」 |
| 反証 | 間違い | レビューで見落とすと事故になる差分 |
| 「同じ期待をした人」（§5） | 補足 | **過去に同じ PR/報告をした人**。メンテナなら当然知っているべき履歴 |
| 終了 | 説明できました | **レビューコメントを書く** → 作者本人の実際の返答（bpo-39554）と並べる |
| README の痛み | AI 成果物が理解できない | **AI が書いた PR をレビューする人**は、まさに「読まずに理解しなければならない人」。物語と現物が一致する |

最後の対比が重要。これまでは「AI の 3000 行を理解する」という語りに対して現物は学習ゲームだったが、**レビュワー**という役を置くと、AI が書いた PR をレビューする日常の痛みに直結する。

### 終了時のレビュー画面

```

    この PR は近道を外すので、1個引数の int 呼び出しの省メモリ経路が消える。」

作者本人の実際の返答（bpo-39554, 2020-02）:

```

プレイヤーの文と本人の文を並べるだけで、採点はしない。**どこまで同じことを言えたかは、本人が見れば分かる。**

### 振る舞いの規則

| 規則 | 値 | 理由 |
| --- | --- | --- |
| デバウンス | 入力停止から 400ms | 実測遅延 220〜750ms。打鍵ごとに叩かない |
| 進行中の要求 | 新しい入力で AbortController により破棄 | 古い読みが後から上書きしない |
| バーを出す閾値 | p ≥ 0.20 | 触れていない軸（0.03〜0.10）を隠す。**軸の一覧を見せない** |
| 帯 | 0.60 以上は濃く、0.40〜0.60 は薄く「読めていない」と添える | `select.ts` の NAMED / UNCLEAR と同じ |
| 全軸が 0.20 未満 | 「まだ何も映っていません」 | 空白より正直 |
| 通信失敗 | バー領域を畳んで「鏡は使えません（送信は可能）」 | フォールバックを既存の T-17 に合わせる |

**軸の一覧を見せない**のが要点。5本を常に並べると「引数の個数による例外」が選択肢として見え、L6 の答えが漏れる。書いたものだけが映れば、鏡は答えを教えない。

| 出力の粒度 | 0.03〜0.97 の連続値 | ほぼ 0 か 1 のみ（temperature 0 でも） |
| 打ちかけ「同じ引数で」 | rule 0.52（まだ読み切れていない） | rule 1.00（断定） |
| 「int か str が1個だけなら」の型軸 | 0.26〜0.35（薄く反応） | 0.00 |
| 所要（warm） | 220〜300ms | 540〜1200ms |

打鍵に追従して棒が 0.5 から 0.9 へ伸びる連続的な手応えは Jev にしか出せない。LLM は打ちかけの文に「まだ半分」を表現できず、打鍵ごとに言い回しが変わってチラつく。よって:

- **棒（Jev）**: 400ms デバウンスで打鍵に追従する。主役
- **声（LLM）**: 句点・読点で止まったとき、または入力が 1 秒止まったときだけ発火する。1文に1回が目安
- 声は Jev の検閲を通してから表示する（次節）

### 漏れの検閲（Jev Noul、1問）

問い: 「`comment` はソフトウェアの実際の振る舞い、または下書きの正誤を述べているか」

| 一言 | 漏れ | 判定 |
| --- | --- | --- |
| 型が違えば別物として扱われます。 | 0.93 | 隠す（最初の実測で gemma4 が実際に出した文） |
| 実際は引数が1個のときだけ 1 と 1.0 が区別されます。 | 0.97 | 隠す |
| その説明だと2個の引数のケースで外れますよ。 | 0.94 | 隠す |
| 型まで厳格に判定する方向ですね。 | 0.11 | 表示 |
| 引数の一致を重視する方向ですね。 | 0.09 | 表示 |
| 例外を1つ置く構えですね。 | 0.09 | 表示 |

閾値 0.30 で隠す。約 200ms なので、声の後ろに直列で挟んでも 1 秒以内に収まる。プロンプトで「言うな」と書いても gemma4 は一度漏らしたので、**検閲は省けない**。

### 画面

```
│ 同じ引数で呼べば記憶を返す。ただし int か str が1個だけなら_        │
├──────────────────────────────────────────────────────────────┤
│ Jev にはこう映っています                                      │
│   引数の値      ████████░░                                    │
│   個数の例外    ███████░░░  （薄い: まだ読み切れていません）  │
│                                                              │
│ 相棒「例外を1つ置く構えですね」                                │
```

- 声は 1 行だけ。棒の下に置き、置き換わるときはフェードで差し替える（点滅させない）
- 声は**質問に答えない**。「これで合ってる？」と聞かれても立場を言うだけ。正誤は事例が示す
- 声が検閲で落ちた・通信に失敗した → 行を空にする。棒だけで成立する設計は §2 のまま

### 効果と危険

- 効果: 「読まれている」実感が最速で立つ。棒は条件、声は構え。両方あると「自分の説明が向こうに届いた」と分かる
- 危険1: 声が「正解の方向」を示唆する誘導になる。→ 立場の言い当てのみ、比較・評価語を禁止、検閲で落とす
- 危険2: 試遊者が声の方を見て棒を読まなくなる。→ 観察点（§8）に追加。起きたら声の頻度を下げる（送信直前のみ）

## 2c. プレイヤーが作る事例 — 「じゃあ f(True) は？」を本物で試す

事例カードは固定 7 枚（＋L8）だが、プレイヤーは §6 の未探索一覧を見て「じゃあこれは？」と言いたくなる。そこで、**プレイヤーが書いた呼び出しの組を、題材コードで実際に実行して新しいカードにする**。

| 段階 | 担当 | 内容 |
| --- | --- | --- |
| 1. 入力 | 人間 | 「f(1.0) のあとに f(True)」のように自然文か式で書く |
| 2. 式への変換 | LLM | `["f(1.0)", "f(True)"]` と `typed` を取り出す。文法は `f(<リテラル>, ...)` のみ許す |
| 3. 検証 | コード | 取り出した式を許可文法でパースし直す（LLM の出力を eval しない）。通らなければ「その形は試せません」 |
| 4. 実行 | コード | WSL の Python で新しいキャッシュを作って実行（`scripts/verify-lru.py` と同じ手順）。結果は remembered / computed / error の実測 |
| 5. 提示 | コード | 現在の仮説からの予想（§3 の規則）と実測を並べてカードにする。相棒の台詞は LLM が書き、検閲を通す |

LLM は「言い換え」と「台詞」だけを担い、**結果は実行で得る**。ここが「vibe でカードを生成する」と「AI が反例を捏造しない」を両立させる線。任意の Python を実行しないため、公開デモでも成立する。

想定通りのシナリオから外れるのは歓迎する。L1〜L7 は「必ず通る道」ではなく「はじめの 4 手の骨格」で、5 手目以降はプレイヤーの疑問で分岐してよい。実装は T-70 とし、時間があれば。

## 3. 事例への当てはめ（コード側の規則）

事例ごとの特徴ベクトル。**実結果は lru-cache.md §3 の実測どおり。**

| 事例 | valuesEqual | sameForm | sameOrder | sameType | fastpathKeyEqual | 実結果 |
| --- | --- | --- | --- | --- | --- | --- |
| L1 `f(1)` → `f(1)` | T | T | T | T | T | 記憶 |
| L2 `f(1)` → `f(1, 0)` | T | F | T | T | F | 計算 |
| L3 `f(1)` → `f(x=1)` | T | F | T | T | F | 計算 |
| L4 `f(x=5,y=6)` → `f(y=6,x=5)` | T | T | F | T | F | 計算 |
| L5 `f(1)` → `f(1.0)` | T | T | T | F | F | 計算 |
| L6 `f(1, 2)` → `f(1.0, 2)` | T | T | T | F | T | **記憶** |
| L7 `typed=True` `f(1, 2)` → `f(1.0, 2)` | T | T | T | F | — | 計算 |

`fastpathKeyEqual` = 「int か str が1個だけなら値そのもの、それ以外は引数の並び」という鍵で比べたときに等しいか。arity 軸はこの列に対応させる。

予想の規則（`select.ts` の構造を維持）:

1. 0.60 以上の軸を named、0.40〜0.60 を unclear とする
2. named も unclear も無ければ **決まらない**
3. named の条件がその事例で**すべて成り立てば「記憶」、1つでも崩れれば「計算」**。arity は fastpathKeyEqual を条件とみなす
4. unclear を含めた場合と含めない場合で予想が変わるなら **決まらない**（既存の strict / loose 比較）
5. **L7 の特例**: type 軸が named でなければ「決まらない」（仮説は `typed=True` という選択肢の存在に触れていない）。type が named なら「計算」
6. L8（unhashable）は事例から外し、未探索に移す（T-62）。どの仮説からも予想できないため

次に出す事例は既存どおり **反証 → 決まらない → 未提示 → 終了**。反証が複数あるときは **配列順（L1→L7）**。差が1つだけの事例から出す並びになっている。

## 10. 証拠の台帳 — 観測が無い体験主張（claim-has-evidence、2026-09-20）

`npm run lint:jev:check` の `claim-has-evidence` が、この文書で「プレイヤーは〜する」と観測なしに書いている節を拾った。reality-check の分類（観測 / 出典 / 推論 / 仮定 / 不明）で言えば、下の行はすべて**仮定**。直せという表ではなく、どの試遊で何を見れば観測に変わるかの表。

| 節 | 主張（要旨） | いまの証拠 | 観測に変える方法 |
| --- | --- | --- | --- |
